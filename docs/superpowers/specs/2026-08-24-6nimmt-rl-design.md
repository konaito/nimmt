# 6 Nimmt! 強化学習AI 設計書

作成日: 2026-08-24

## 1. 目的とスコープ

カードゲーム「ニムト（6 Nimmt!）」を高い水準でプレイするAIを、自己対戦による強化学習で作る。

**主戦場**: 4人戦と2人戦（1モデルで両対応。プレイ人数を入力特徴に含める）
**目的関数**: 1ディール（10ターン）で自分が取る牛頭の合計を最小化する
**成果物**: 環境実装・ベースラインbot群・評価ハーネス・学習コード・学習済み重み・評価レポート・CLI対戦

**スコープ外（今回やらない）**
- 66点到達までの複数ディール通算ゲーム（将来の拡張として設計は妨げない）
- Web UI
- 3人/5人以上の人数（モデルは人数を特徴に持つので後から追加学習可能）

### 1.1 「最強」の定義についての明示

4人戦のニムトは **非ゼロサムかつ不完全情報の多人数ゲーム** であり、ナッシュ均衡は計算不能であるうえ、複数均衡が存在するため「理論的最強」は定義できない。本プロジェクトでの「強さ」は次の実測値としてのみ定義・報告する。

1. ベースラインbot群に対する平均失点差とディール勝率（95%信頼区間つき）
2. 学習チェックポイント同士の総当たりによるEloレーティングの単調性

この前提を最初に固定する。評価ハーネスが出した数字以外を「強さ」の根拠として報告しない。

## 2. ゲームルール（一次ソースで確認済み）

出典: [6 nimmt! - Wikipedia](https://en.wikipedia.org/wiki/6_nimmt!), [UltraBoardGames 公式ルール](https://www.ultraboardgames.com/6-nimmt/game-rules.php)

- カードは 1〜104 の104枚。
- 牛頭（ペナルティ点）の分布:

  | 牛頭 | 対象 | 枚数 |
  |---|---|---|
  | 7 | 55 | 1 |
  | 5 | 11の倍数（55を除く: 11,22,33,44,66,77,88,99） | 8 |
  | 3 | 10の倍数（10,20,...,100） | 10 |
  | 2 | 5の倍数のうち上記以外（5,15,25,35,45,65,75,85,95） | 9 |
  | 1 | その他 | 76 |
  | | **合計** | **104枚 / 総牛頭 171** |

- 2〜10人。各プレイヤーに10枚配り、場に4枚を並べて4つの列の起点とする。残りは箱に戻す。
- 毎ターン全員が同時に1枚を伏せて出し、一斉に公開する。
- 公開されたカードを **数字の昇順に1枚ずつ** 処理する。
- 配置先: 「行末のカードが、出したカードより小さい」行のうち、**行末が最も大きい（＝最も近い）行**。
- その行に既に5枚あるとき（自分のカードが6枚目）: その5枚を引き取り、自分のカードだけが残って新しい行の起点になる。
- 出したカードがどの行末よりも小さいとき: **プレイヤーが行を1つ選んで** その行のカードを全て引き取り、自分のカードだけが残って新しい行の起点になる。
- 10ターンで手札が尽きてディール終了。引き取ったカードの牛頭合計が失点。

## 3. アーキテクチャ全体

```
6nimmt/
  env/         ベクトル化ゲーム環境（NumPy）
  bots/        ベースラインbot群（random / greedy / heuristic / mc-rollout）
  eval/        評価ハーネス（重複配牌方式・Eloリーグ）
  rl/          PPO自己対戦学習（PyTorch）
  cli/         対人対戦CLI
  tests/       ルール正当性のユニットテスト
```

依存の向き: `env` は何にも依存しない。`bots` / `rl` は `env` に依存する。`eval` は `env` と `bots` と `rl` の推論部にのみ依存し、学習には依存しない。

**スタック**: Python 3.12 / NumPy / PyTorch。パッケージ管理は uv。

## 4. 環境（env）

### 4.1 ベクトル化方針

B ゲーム（既定 2048）× P プレイヤーを同時にシミュレートする。学習のボトルネックはニューラルネットではなく環境シミュレーションであるため、ここが全体のスループットを決める。

内部状態（すべて NumPy 配列）:

| 名前 | 形状 | dtype | 意味 |
|---|---|---|---|
| `rows` | (B, 4, 5) | int16 | 各行のカード。未使用は0 |
| `row_len` | (B, 4) | int8 | 各行の枚数（1〜5） |
| `hands` | (B, P, 10) | int16 | 手札。出したカードは0 |
| `taken` | (B, P) | int16 | このディールで引き取った牛頭累計 |
| `seen` | (B, 104) | bool | 全員に既知のカード（場・引き取り済み） |
| `turn` | scalar | int | 0〜9 |

1ターンの解決は「公開された P 枚を昇順に処理」する。k = 0..P-1 のループになるが、**各 k のステップで B ゲーム全部を一括処理できる**（P ≤ 4 なので反復は最大4回）。

### 4.2 二相ステップ（重要）

プレイヤーの意思決定は2種類ある。

1. **カード選択** — 手札から1枚選ぶ。行動空間は残り手札枚数（≤10）。
2. **行選択** — 出したカードが全行末より小さいとき、引き取る行を4つから選ぶ。行動空間は4。

行選択は **全員のカードが公開された後** に発生するため、カード選択と同時に決めさせると公開情報を捨てることになる。よって env は phase を持ち、行選択が必要になったゲームだけをまとめてポリシーに問い直す。

```
obs = env.reset()                    # phase = CARD
while not done:
    if env.phase == CARD:
        actions = policy.pick_card(obs)      # (B, P)
    else:  # phase == ROW
        actions = policy.pick_row(obs)       # 該当ゲームのみ (M,)
    obs, reward, done = env.step(actions)
```

行選択が発生するのは1ディールあたり数回なので、フォワードパスの追加コストは小さい。

### 4.3 ルール正当性テスト

`tests/test_rules.py` に以下を置き、実装前に書く（TDD）。

- 牛頭関数: 55→7、11の倍数→5、10の倍数→3、5の倍数→2、その他→1。1〜104の合計が171。
- 配牌: 104枚が重複なく一意に配られ、手札10枚×P + 場4枚 が全て相異なる。
- 配置: 行末が最も近い上位の行に置かれる。
- 6枚目: 5枚ある行に置くと、その5枚の牛頭を引き取り、行が自分のカード1枚にリセットされる。
- 全行より低い: 選んだ行の全カードを引き取り、行がリセットされる。
- 昇順解決: 出された順ではなく数字の昇順に処理される（小さいカードが先に6枚目を踏むケースで検証）。
- ディール終了時、全プレイヤーの失点合計 ≤ 171。

**参照実装との突き合わせ**: ベクトル化実装とは別に、素直な逐次実装（`env/reference.py`）を書き、ランダム対戦10万ディールで両者の失点が完全一致することを確認する。ベクトル化のバグはテストをすり抜けやすいため。

## 5. 状態・行動の表現

### 5.1 カードごとのスコアリング方式

104次元の固定出力ヘッドは使わない。手札枚数が可変であること、カード値をまたいだ汎化が効くことから、**手札の各カードを個別にスコアリングする**。

```
logit_i = f( concat[ global_embedding , card_feature_i ] )     i ∈ 残り手札
p = softmax(logit)   # 出したカードはマスク
```

行選択も同じ形。4行それぞれを `g( concat[global_embedding, row_feature_j] )` でスコアリングする。

### 5.2 グローバル特徴

- 4行それぞれの (行末カード値/104, 枚数/5, 行の牛頭合計/正規化, 枚数のone-hot 5次元)
- 自分の手札: 104次元 multi-hot
- **既知の死にカード: 104次元 multi-hot**（場にある + 引き取られた + 自分の手札）。未見カードの分布はこれの補集合として推論できる
- 各プレイヤーの現在失点（自分を先頭に並べ替え）
- ターン番号 one-hot（10次元）
- プレイヤー人数 P（正規化スカラ + one-hot）

### 5.3 カードごとの特徴

env が候補カードごとに計算する。

- カード値 / 104、牛頭 / 7
- 「今この瞬間に単独で出したとき」の行き先の行: その行の枚数、その行の牛頭合計、行末との差（gap）
- 6枚目になるか（bool）
- 全行末より小さいか（bool）
- そのカードより小さい未見カードの枚数 / 残り未見枚数
- **そのカードより小さく、かつ同じ行に入りうる未見カードの枚数** — 割り込まれリスクの直接的な代理変数。ここが効くと想定している（要検証）

### 5.4 ネットワーク

- global encoder: MLP 2層、隠れ 256〜512、活性化 GELU、LayerNorm
- card head / row head: それぞれ MLP 2層 → スカラ
- value head: MLP 2層 → スカラ。V(s) は「このディールで自分が今後取る牛頭の負値」を予測する

パラメータ数は数十万オーダー。M4のメモリには余裕で載る。

## 6. 学習

### 6.1 報酬

- 密報酬: 各ターンに自分が引き取った牛頭の負値を、そのターンの報酬とする。
- γ = 1.0。リターンは 1ディールの総失点の負値と一致する。
- スケーリング: 報酬を定数（例 10）で割る。

**アブレーション**: 相対報酬 `-(自分の失点 - 他プレイヤー失点の平均)` を別ランで学習し、評価ハーネスで比較する。絶対失点の最小化は「全員が低失点に収まる」共存解に寄る可能性があるため、実測で確認する。デフォルトは指定通り絶対失点最小化。

### 6.2 アルゴリズム

PPO（clip 0.2, GAE λ=0.95, γ=1.0）。

- **全席パラメータ共有**: 全プレイヤーが同一ネットで行動する。経験が P 倍集まる。
- **entropy 係数を減衰**（0.02 → 0.002）。同時手番ゲームは決定的方策に落ちると読まれるため、探索を維持する。
- ミニバッチ: 2048ゲーム × 10ターン × P席 の経験を1イテレーションで収集し、数エポック回す。

### 6.3 リーグ（自己対戦の脆さ対策）

純粋な自己対戦だけだと方策が循環し、特定の戦術に脆くなる。対戦相手の一部を過去チェックポイント（凍結）からサンプリングする。

- ゲームの 50% は全席が現方策（純自己対戦）
- ゲームの 50% は 1席が学習者、残りは過去チェックポイントプールから一様サンプル
- 凍結相手の経験は学習に使わない（学習者の席の経験のみ収集）
- チェックポイントは一定イテレーションごとにプールへ追加、プール上限20（古いものからFIFOで捨てる）

## 7. ベースラインbotと評価

**評価ハーネスは学習より先に実装する。** これがないと強さを報告できない。

### 7.1 ベースライン

| 名前 | 方策 |
|---|---|
| `random` | 手札から一様ランダム |
| `greedy` | 「今単独で出したときに引き取る牛頭」が最小のカード |
| `heuristic` | 行末に最も近い上のカードを優先。行が5枚に近い場合は避ける。終盤に小カードを抱えないよう処理。行選択は牛頭最小の行 |
| `mc-rollout` | 未見カードから相手の手札をサンプリングし、候補カードごとに残りディールをプレイアウトして期待失点が最小のものを選ぶ。**最終評価では相手手札のサンプル数を24にする**（8では分散で頭打ちになり、完了条件のゲートが不当に緩くなる。実測: サンプル数 1/2/8/24 で mc − heuristic = +1.048 / +0.679 / −1.276 / −2.697） |

### 7.2 評価ハーネス

- **重複配牌方式**: 固定シードで生成した配牌セット（既定 20,000ディール）を全botに同一に割り当て、席順をローテーションさせる。同じ配牌を全員が経験するので分散が大幅に下がり、少ない試行で有意差が出る。
- 指標: 平均失点、ディール勝率（そのディールで最少失点だった率、同点は分割）、対ベースライン差の95%信頼区間。
  CIは**「AIの失点 − 同じディールでの相手席の平均失点」を1本の系列にして**対応ありブートストラップする。席ごとにCIを出して境界を平均したものはCIではない。
- **Eloリーグ**: 学習チェックポイント同士を総当たりさせ、Eloが単調に上がっているかを確認する。学習が進んでいることの独立した確認になる。ペア数が O(n²) になるので、チェックポイントは等間隔に10個程度へ間引く。
- **最終レポートの配牌シードは、学習中のモニタリングで使ったシードと別にする。** 同じ配牌で見出し数字を出すと、モデル選択に使った盤面で自己採点することになる。

### 7.3 完了条件

以下をすべて満たしたときに「完成」と報告する。

1. ルール正当性テストが全て通り、参照実装とベクトル化実装が10万ディールで一致する
2. 学習方策が 4人戦で `heuristic` および `mc-rollout` に対し、平均失点で統計的に有意に優越する（95%CIが0を跨がない）
3. チェックポイントのEloが単調増加している
4. 2人戦でも同様に `heuristic` を上回る

報告時には「何をどう確かめたか」を必ず併記する（テストが通った / 何ディール対戦させた / CIはいくつ）。

## 8. リモート実行（REMOTE_HOST）

**実測済みのリモート環境**: Apple M4 / 10コア / 16GB / macOS 26.4 / Python 3.9.6 のみ / uv 未インストール

### 8.1 セットアップ

1. `uv` をインストールし、Python 3.12 を導入する
2. コード同期は `rsync`（`.venv` と `runs/` は除外）
3. 学習は `tmux` セッション内で実行。チェックポイントとJSONLログを `runs/<run_id>/` に出力
4. ログはローカルに rsync で回収して集計する

### 8.2 速度ベンチ（学習前に必ず実施）

**仮定せず実測する。**

- env の steps/sec（B = 512 / 2048 / 8192 で測定）
- ネットのフォワード/バックワードを **CPU と MPS の両方で測定**。小バッチのMLPではCPUがMPSより速いことが多いため、速い方を採用する
- env とネットのどちらがボトルネックかを確認し、env 側なら `multiprocessing` で env worker を分ける（10コア）

このベンチ結果を見てから B とネットサイズを確定する。
